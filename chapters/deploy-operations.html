8  Deploy & Operations

8.1 Routine Deploy

On the VM:

cd /home/yeroslaviz/BCFMS-project-management
git pull origin main
./scripts/deploy.sh

The deploy script syncs ms-app/ to /srv/shiny-server/ms-app/, excludes ms_projects.db and .Renviron, fixes ownership, restarts Shiny, and runs HTTPS/LDAP smoke tests unless SKIP_SMOKE_TEST=1.

8.2 Pre-Deploy Backups

Routine deployment excludes the database, but preserve the currently deployed code and Apache configuration before risky maintenance:

sudo rsync -av --exclude 'ms_projects.db' /srv/shiny-server/ms-app/ /srv/shiny-server/ms-app.backup_$(date +%Y%m%d_%H%M)/
sudo cp /etc/apache2/sites-enabled/ms-vm-shiny-443.conf /etc/apache2/sites-enabled/ms-vm-shiny-443.conf.backup_$(date +%Y%m%d_%H%M)

For database maintenance, machine migration, or disaster recovery, also create the verified database and upload backups described in Database backup and exact recovery.

8.3 Restart Services

sudo systemctl restart shiny-server
sudo systemctl restart apache2

8.4 Smoke Tests

curl -Ik https://mscf-vm.biochem.mpg.de/
curl -Ik -u USER https://mscf-vm.biochem.mpg.de/ms-app/
curl -I http://127.0.0.1:3838/ms-app/

Optional non-interactive LDAP smoke test:

LDAP_TEST_USER="yeroslaviz-test" LDAP_TEST_PASSWORD="YOUR_PASSWORD" ./scripts/deploy.sh

Skip smoke tests only when needed:

SKIP_SMOKE_TEST=1 ./scripts/deploy.sh

Override the public URL:

PUBLIC_BASE_URL="https://mscf-vm.biochem.mpg.de" ./scripts/deploy.sh

8.5 Database Behavior

Deploy is code-only. It does not rebuild or overwrite ms_projects.db.

To initialize a missing database or apply migrations and seed checks to an existing database:

cd /srv/shiny-server/ms-app
sudo -u shiny Rscript setup_database.R

Existing rows are preserved by default. Never set MS_RESET_DB=1 during a routine deployment. That setting deliberately deletes and rebuilds the target database.

Dropdown terms and their costs are runtime database content. Administrators can add, rename, deactivate, delete, and reinstate them without rebuilding the database. See Dropdown Terms & Costs for the interface workflow and the direct-database recovery procedure.

Changes to code constants such as MS_SUBMISSION_WARNING take effect after deployment restarts Shiny. The current warning is:

Samples are stored for a maximum of 2 months after analysis is completed, then discarded without further notice.

Changes to ms_landing_text_defaults require an explicit one-time synchronization because existing landing-page rows are preserved during normal startup. Confirm that the desired defaults are present in the deployed db_schema.R, then run:

cd /srv/shiny-server/ms-app
sudo -u shiny Rscript apply_content_defaults.R
sudo systemctl restart shiny-server

This updates the title, body, and display order of the standard landing blocks to match db_schema.R; it preserves other landing blocks and each block’s active/inactive state. Running setup_database.R alone does not replace existing landing text because routine seed checks use INSERT OR IGNORE.

8.6 Database backup and exact recovery

The database seed definitions reproduce application defaults, not the current production state. To retain every current project, sample, dropdown option, custom cost, user, and status-history row, preserve a transactionally consistent SQLite snapshot.

Uploaded files are stored outside SQLite. A complete recovery therefore needs:

  1. The verified SQLite backup.
  2. A backup or storage snapshot of MS_UPLOAD_ROOT.
  3. A backup of MS_LOCAL_UPLOAD_FALLBACK.
  4. The runtime configuration that defines those paths.

8.6.1 Create a verified database backup

Run the backup script from the repository checkout. Store backups outside the deployed application directory so deployment and code rollback cannot remove them:

cd /home/yeroslaviz/BCFMS-project-management
sudo install -d -o shiny -g shiny -m 750 /srv/ms-app-data/db-backups
backup_file="/srv/ms-app-data/db-backups/ms_projects_$(date +%Y%m%d_%H%M%S).sqlite"
sudo -u shiny Rscript scripts/backup_database.R \
  /srv/shiny-server/ms-app/ms_projects.db \
  "$backup_file"
sudo -u shiny sqlite3 "$backup_file" 'PRAGMA integrity_check;'
sudo -u shiny sha256sum "$backup_file"

The backup script uses SQLite’s backup mechanism and refuses to overwrite an existing destination. Both integrity checks must return ok. Record the SHA-256 checksum with the backup.

Back up the persistent fallback upload directory during the same maintenance window:

sudo rsync -av /srv/ms-app-data/uploads_pending_pool/ /secure/backups/uploads_pending_pool/

Back up MS_UPLOAD_ROOT using the facility storage system’s snapshot or backup procedure. Do not assume that the SQLite backup contains project uploads.

8.6.2 Test a recovery

Restore to a separate path first:

cd /srv/shiny-server/ms-app
sudo -u shiny env \
  MS_DB_FILE=/private/tmp/ms_projects_restore_test.db \
  MS_RESTORE_DB_FROM=/srv/ms-app-data/db-backups/ms_projects_YYYYMMDD_HHMMSS.sqlite \
  Rscript setup_database.R
sudo -u shiny sqlite3 /private/tmp/ms_projects_restore_test.db 'PRAGMA integrity_check;'

Compare important table counts between production and the test restore:

for table in projects project_samples controlled_options option_costs users project_status_history; do
  printf '%-28s production=' "$table"
  sudo -u shiny sqlite3 /srv/shiny-server/ms-app/ms_projects.db "SELECT COUNT(*) FROM $table;"
  printf '%-28s restored=' "$table"
  sudo -u shiny sqlite3 /private/tmp/ms_projects_restore_test.db "SELECT COUNT(*) FROM $table;"
done

Remove the temporary test database after the comparison.

8.6.3 Restore production or move to another machine

Deploy the application code and configure .Renviron first. Restore the upload directories to the same configured paths, then restore the database:

sudo systemctl stop shiny-server
cd /srv/shiny-server/ms-app
sudo -u shiny env \
  MS_DB_FILE=/srv/shiny-server/ms-app/ms_projects.db \
  MS_RESTORE_DB_FROM=/secure/backups/ms_projects.sqlite \
  MS_RESET_DB=1 \
  Rscript setup_database.R
sudo -u shiny sqlite3 /srv/shiny-server/ms-app/ms_projects.db 'PRAGMA integrity_check;'
sudo systemctl start shiny-server

MS_RESET_DB=1 is required here only because an existing target is being intentionally replaced by a verified backup. After restoration, setup_database.R applies any schema migrations and seed defaults required by the deployed application version.

8.7 Rollback

This rollback restores application code only and leaves the current database in place:

sudo systemctl stop shiny-server
sudo rsync -av --delete --exclude 'ms_projects.db' /srv/shiny-server/ms-app.backup_YYYYMMDD_HHMM/ /srv/shiny-server/ms-app/
sudo chown -R shiny:shiny /srv/shiny-server/ms-app
sudo systemctl start shiny-server
sudo systemctl restart apache2

If the database itself must be rolled back, use the verified restore procedure above rather than copying a potentially active SQLite file.
